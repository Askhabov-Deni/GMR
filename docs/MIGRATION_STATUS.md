### Решения Фазы 1
- try/except ImportError вместо чисто относительных импортов: чисто относительные
  сломали бы запуск `python models/cnn/train_cnn.py` ("no known parent package").
  Побочный эффект: `except ImportError` может замаскировать реальную ошибку
  импорта внутри самого модуля — если увидишь странный ImportError про `config_*`,
  ищи причину в первой ветке.
- tqdm не в основных зависимостях: используется только в `utils/compute_mean_std.py`,
  а в окружении агента не установлен, версию проверить было нечем.
- Версии в `requirements.txt` — точные (`==`) те, на которых прошли тесты; у
  владельца стоят Python 3.14 и torch 2.14.0, albumentations был 1.4.18.

## Найденные баги (продолжение)
- 2026-09-28 — **albumentations 1.4.18 молча игнорирует `A.GaussNoise(std_range=...)`**
  (`models/cnn/dataset_cnn.py`, `_train_transform`): выдаёт UserWarning
  "Argument 'std_range' is not valid and will be ignored", а не ошибку. На 2.0.8
  параметр принимается. Проверено в песочнице на обеих версиях. У владельца в

  шум в аугментации был не тот, что записан в коде. Какая версия использовалась

  Golden tests этот код не покрывают (аугментации не вызываются).

### Решения Фазы 2b
- SQLite пересоздаётся из CSV в начале каждого shadow-прогона: `program2.py`
  правит CSV-лог напрямую (ручная верификация), и без пересоздания эти
  правки выглядели бы как расхождения, хотя ошибки в коде нет.
- Сверка — один раз в конце прогона, а не после каждой строки: построчная
  сверка читает оба хранилища целиком, на тысяче фото это O(n²) чтений CSV.
- `DuplicatePolicy` (кейсы 5-8, в т.ч. кейс 8 — рассинхронизация таблицы и
  лога) по-прежнему получает строки лога только из CSV. Лишняя строка в
  SQLite не может изменить ни одно решение — отдельный тест
  `test_shadow_reads_only_from_primary`.

### Откат Фазы 2b на CSV (критерий готовности ТЗ)
Источник истины не переключался — CSV-лог остаётся главным, SQLite только
дублирует запись. Поэтому откат не требует переноса данных:
1. Выключить shadow-режим: `shadow_sqlite_log = False` (это значение по
   умолчанию) — пайплайн пишет только в CSV, как до Фазы 2b.
2. Файлы `<таблица>_log.sqlite` и `<таблица>_log_shadow_report.txt` можно
   удалить — они ни на что не влияют (и уже в `.gitignore`).
3. Если нужно убрать и код: `git revert` коммита Фазы 2b. Формат CSV-лога
   до и после Фазы 2b одинаковый байт-в-байт (тест
   `test_csv_*_identical_bytes_to_old_implementation`), поэтому логи,
   записанные новым кодом, читаются старым без изменений.
Когда (и если) источник истины переключат на SQLite, этот раздел нужно
будет переписать: откат тогда потребует выгрузки SQLite обратно в CSV.

## Как мы работаем (для новой сессии агента, 2026-09-29)
Сложилось за сессии, в которых сделаны фазы 0–3. Не догма, но без причины
не менять.

**Окружение владельца.** Windows, PowerShell, Python 3.14, venv `.venv` в
`C:\AD\GSM\gas-meter-reader`. Рабочие данные для прогонов —
`data_for_reader_test/` (в `.gitignore`): `input/` с подпапками операторов
(Али Сагаев, Аюб, Магомед Айдамиров, Магомед Кубаев, Сулиман С, Фатима Я —
1111 фото), `meters_table.csv`, `meters_table_log.csv`. Модель цифр —
`v3_platinum`. `pip.exe` в venv может быть сломан после переноса папки —
использовать `python -m pip`.

**Доставка изменений.** У агента нет push-доступа. Агент клонирует
`https://github.com/Askhabov-Deni/GMR`, работает поверх последнего коммита
`main`, собирает `git diff` в патч, проверяет его на свежем клоне
(`git apply --check`, `git apply`, `pytest`), отдаёт файлом. Владелец:
`git apply <патч>` → `python -m pytest tests/ -v` → commit → push.
Перед сборкой патча агент сверяется с GitHub: если владелец менял код сам
(бывает — например, пути моделей в `PipelineConfig`), патч собирается от его
коммита. Однажды патч, собранный от устаревшей базы, при `--3way` дал
сломанный гибрид `reader.py` — после этого правило соблюдается всегда.

**Проверка.** Каждое изменение — тесты + мутационная проверка (намеренно
ломаем новую логику, убеждаемся, что тест падает). Изменения поведения
подтверждаются на реальных данных: агент заранее считает прогноз по логу
владельца, владелец присылает `report.txt` / лог, сверяем.

**Изменения поведения** (не рефакторинг) — только решением владельца,
отдельным коммитом вне фаз, с записью в этот файл. Агент предлагает
варианты с плюсами и минусами, владелец выбирает.

**Общение.** По-русски. Владелец — не профессиональный разработчик, но
быстро разбирается; объяснять суть и последствия, без лишнего жаргона.
Команды для PowerShell давать готовыми к копированию.
