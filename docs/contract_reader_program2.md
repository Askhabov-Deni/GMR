# Стык reader.py ↔ program2.py

Что `reader.py` оставляет на диске и что с этим делает `program2.py`.
Любая переделка `program2.py` (владелец ожидает её в будущем) обязана
сохранить всё, что описано здесь. Иначе автоматическая и ручная обработка
перестанут понимать друг друга.

Проверяется тестами:
- `tests/test_program2_processing.py` — вкладка «Обработка»;
- `tests/test_program2_verify.py` — вкладка «Проверка», «Серийник в базе с
  ошибкой», подсказка;
- `tests/test_photo_identity.py` — отпечаток в ручных строках;
- `tests/test_shadow_run_pipeline.py` — `reader.py` не возвращает
  разобранное фото в `question/`.

Составлено в Фазе 6 (2026-09-30) по коду и тестам.

## 1. Три общих файла и папка

| Что | Где | Кто пишет |
|---|---|---|
| Таблица счётчиков | путь `table_path` (CSV или XLSX) | `reader.py` — «Текущие показания» при PLUS/MINUS; `program2.py` — при «Принять» и исправлении на «Проверке» |
| Лог обработки | `<таблица>_log.csv` рядом с таблицей | `reader.py` — строки `source=auto`; `program2.py` — строки `source=manual` и отметки проверки в авто-строках |
| Папка результатов | `output/<контролёр>/…` (или `output/…` в режиме одной папки) | `reader.py` раскладывает, `program2.py` разбирает |
| Настройки program2 | `settings.json` рядом с `program2.py` | `program2.py` (оператор, папка с фото, таблица, папка разметки) |
| Копии таблицы и лога | `gmr_backups/<имя таблицы>/<дата_время>/` рядом с таблицей, последние 30 | `reader.py` — перед прогоном; `program2.py` — при запуске окна |
| Журнал прогона | `<папка результатов>/run_logs/run_<дата_время>.txt`, последние 30 | `reader.py` |

`program2.py` работает с **одной** папкой контролёра: «Папка с фото» =
`output/<контролёр>`. Если указать общую `output/`, увидите «0 из 0».

## 2. Таблица

Столбцы задаются в `PipelineConfig` (`src/gmr/domain/config.py`):

| Столбец | Роль |
|---|---|
| `Номер счетчика` (`col_serial`) | серийник; сравнивается как текст, ведущие нули важны (`normalize_serial` — только `strip`) |
| `Лицевой счет` (`col_account_id`) | лицевой счёт; имя итогового фото = `<лицевой счёт>.<расширение>` |
| `Последние показания` (`col_last_reading`) | для расчёта расхода; только читается |
| `Текущие показания` (`col_new_reading`) | **сюда пишется результат** (число без ведущих нулей) |

Чтение и запись — `src/gmr/storage/table.py` (`load_table`/`save_table`,
CSV пишется с `QUOTE_ALL`). Поиск серийника у обоих одинаковый: номер,
`'0'+номер`, `'00'+номер`.

## 3. Раскладка папки контролёра

| Папка | Кто кладёт | Что это |
|---|---|---|
| `plus/`, `minus/` | `reader.py` (PLUS/MINUS), `program2.py` («Принять», исправление) | показание записано в таблицу; файл `<лицевой счёт>.jpg` |
| `repeat/` | `reader.py` (REPEAT), `program2.py` («Дубль») | дубль |
| `question/<причина>/` | `reader.py` | на ручной разбор. Причины: `digits_error`, `suspicious`, `serial_low_conf`, `serial_not_found`, `no_serial`, `no_meter`, `error` (`OUTCOME_FOLDER`; `error` — программа упала на этом фото, с 2026-10-01). Порядок очереди в `program2.py` — по этому списку (`QUESTION_SUBFOLDERS`) |
| `unreadable/` | `program2.py` («Нечитаемо») | |
| `not_in_db/` | `program2.py` («Нет в базе») | |
| `db_serial_fix/` + `db_serial_fix.csv` | `program2.py` («Серийник в базе с ошибкой») | показание **не** записано; список для исправления базы («;», Excel): Фото; Контролёр; Лицевой счёт; Серийник в базе; Серийник на фото; Показание; Дата; Оператор |
| `report.txt` | `reader.py` | отчёт прогона по папке |

Имя файла в `question/`: `final_filename` авто-строки, а если он пустой —
`original_filename`. Для NO_METER, NO_SERIAL, SERIAL_LOW_CONF,
SERIAL_NOT_FOUND и ERROR он пустой, потому что лицевой счёт ещё не известен.
По этому имени `program2.py` находит авто-строку, породившую файл
(`find_auto_row_for_output_file`).

## 4. Лог

Столбцы — `LOG_COLUMNS` (`src/gmr/storage/log_store.py`), порядок не менять,
новые столбцы добавлять только в конец:
`original_filename, final_filename, serial_id, account_id, reading,
last_reading, delta, outcome, source, processed_by, processed_at,
verified_by, verified_at, model_serial_conf, model_reading_str, notes,
photo_hash, source_folder`.

### source
| Значение | Кто | Смысл |
|---|---|---|
| `auto` | `reader.py` | результат автоматической обработки |
| `manual` | `program2.py` | решение оператора по фото из `question/` |
| `pre_existing` | `reader.py` (однократно) | строки, созданные из уже заполненной таблицы при первом запуске (`original_filename=__pre_existing__`) |

### outcome
- `source=auto`: `PLUS, MINUS, REPEAT, NO_METER, NO_SERIAL, SERIAL_LOW_CONF,
  SERIAL_NOT_FOUND, DIGITS_ERROR, SUSPICIOUS, ERROR` (`ERROR` — с 2026-10-01:
  программа упала на фото; `notes` — «ошибка программы: …»; при следующем
  прогоне фото читается заново, как любая авто-ошибка).
- `source=manual`: `PLUS, MINUS` («Принять»; SUSPICIOUS после подтверждения
  становится PLUS/MINUS), `REPEAT` («Дубль»), `UNREADABLE`, `NOT_IN_DB`,
  `DB_SERIAL_FIX`.

### Поля, на которые опираются обе программы
- `photo_hash` (первые 16 hex SHA-256 исходного файла) и `source_folder`
  (подпапка контролёра). В авто-строке их пишет `reader.py`. В ручную
  строку `program2.py` **копирует** их из авто-строки, породившей файл в
  `question/`: сам файл там пересохранён с подписью, и отпечаток по нему
  не посчитать. Без этого `reader.py` не узнает разобранное фото.
- `model_reading_str` — что прочитала модель; **никогда не перезаписывается**
  при ручной правке. Это эталон для `tools/analyze_log.py`.
- `verified_by` / `verified_at` — отметка на вкладке «Проверка», ставится
  в авто-строку PLUS/MINUS этого фото.
- `notes`:
  - авто — причина исхода; плюс `| подставлено: posN='5' (цифра не найдена),
    posM='0' (прочитано 7, conf=…)` для подставленных цифр;
  - копия файла в прогоне — `duplicate file in current run`;
  - ручные: причина (имя подпапки `question/`), `| подсказка: <номер>`,
    `счётчик не найден в базе`, `нечитаемо (из списка)`,
    `серийник в базе с ошибкой: в базе X, на фото Y`;
  - проверка: `| исправлено при проверке` (при смене абонента —
    `(абонент X → Y)`).

## 5. Правила, которые связывают программы

1. **Разобранное фото не возвращается** (шаг 0 `reader.py`,
   `ProcessedPhotoPolicy`). Фото узнаётся по `photo_hash`, у старых строк —
   по имени. Если по нему есть строка `source=manual` с любым исходом или
   авто-строка PLUS/MINUS/REPEAT (кроме копий в прогоне), это REPEAT, модели
   не запускаются. Если есть только авто-ошибки, фото обрабатывается заново.
2. **Дубли по лицевому счёту** (`DuplicatePolicy`, шаг 4, по порядку):
   счёт уже обработан в этом прогоне — REPEAT. Иначе, если «Текущие
   показания» в таблице заполнены: есть строка `pre_existing` или строка
   PLUS/MINUS по этому счёту (авто **или ручная** — поэтому «Принять» в
   program2 закрывает счёт) — REPEAT; ни одна строка лога значение не
   объясняет — SUSPICIOUS (рассинхронизация таблицы и лога).
3. **Вкладка «Проверка»** показывает фото из `plus/`/`minus/`, у авто-строки
   которых исход совпадает с папкой и `verified_by` пуст. Строки REPEAT того
   же счётчика не подходят.
4. **Исправление на «Проверке»** пишет новое показание в таблицу. Если
   серийник другой, показание переносится к найденному абоненту (с
   подтверждением), у прежнего стирается, только если там всё ещё значение
   `reader.py`.
5. **«Серийник в базе с ошибкой»** в таблицу не пишет. Показание — в логе и
   в `db_serial_fix.csv`, вносится вручную после исправления базы.
